Chapter I

The First Lie

Two functions look the same. They probably aren’t. The cost of pretending they are is the cost we keep paying.

The most expensive sentence in any codebase is “I noticed these two are doing the same thing.” It is expensive because it is, in almost every case, a misreading of the present. The two callers were not the same. They were the same on Tuesday.

I have spent ten years watching engineers (myself among them) take two functions, see structural similarity, and extract a third function that purports to handle both. Six months later, one of the original callers needed to do something the other did not. The shared function grew a parameter. Six months after that, another. The function signature became a list of every difference between two domains that, in retrospect, never had a reason to share an implementation.

What looked the same

Consider the canonical case: validating a user-submitted form, and validating an admin-submitted form. The fields overlap. The rules look the same. You write a single validate(form) and feel proud.

fn validate(form: &Form) -> Result<Valid, Vec<Error>> {
    let mut errors = Vec::new();
    if form.email.is_empty() { errors.push(Error::EmailMissing); }
    // ... 40 more rules
    if errors.is_empty() { Ok(Valid(form.clone())) } else { Err(errors) }
}

Then a product manager appears. The admin form, it turns out, allows blank emails for service accounts. The function grows a flag. Then another, for the case where users can have email but admins must. Then a third, when localization changes the error messages but only for one path.

None of these are bugs. They are the abstraction performing exactly as designed. The design was wrong.

Chapter II

The Cost of the Wrapper

Every shared abstraction is a coupling. The question is whether that coupling buys more than it costs.

Software is not free to abstract. The cost is paid in three currencies, and engineers, in our enthusiasm for the first one, almost never count the other two.

Currency one: indirection

To read shared code, you must follow references. Each call site lives elsewhere. Each test of behavior must be staged through the wrapper’s contract. A reader who wants to know what happens when an admin submits a form must hold three layers in their head: the call site, the shared validator, the rules tables it consults. None of this is wrong. All of it is a tax.

Currency two: lock-in

The shared abstraction freezes the contract. Once two callers consume validate(form, opts), changing its signature changes both. That sounds like the upside — one change, two beneficiaries — but it is the same fact described positively. When admin needs a new rule, the user-facing path is dragged along. When the user-facing path needs a faster code path, admin is dragged with it.

“Premature abstraction is more expensive than premature optimization, because it is harder to undo and easier to convince yourself was correct.”

Currency three: epistemic

The most insidious cost. Two functions that look alike, having been merged, can no longer teach you that they were ever different. The seam is gone. New engineers inherit a single function and assume the unification reflects a deeper truth. They reason from the abstraction, not from the cases it was made of. They become, in effect, abstraction-poisoned: they cannot see the domain through the API.

Chapter III

When to Extract

There are honest reasons to share code. They are rarer than you think, and none of them are “these two functions look similar.”

Here are the three signals I have come to trust, after a decade of getting it wrong in both directions.

Signal one · The third caller

Two duplicates is data. Three duplicates is a pattern. The classic rule of three exists because it is the smallest sample that distinguishes coincidence from structure. If you are about to write the third copy, stop — that is the moment a shared abstraction earns its rent.

Signal two · A real invariant

Sometimes two callers must behave the same way because the system depends on it. Authentication checks that must agree. Serialization that must round-trip. Money calculations that must sum to a known total. These are not similar — they are tied. Sharing the implementation is not aesthetic, it is correctness.

Signal three · A name that survives

The hardest signal, and the one I wish I had learned earlier. A good abstraction has a name that you would have used even if you had been writing the second caller from scratch. send_welcome_email survives. process_user does not. If you cannot name the abstraction without referring to the callers it unifies, you are not extracting a concept — you are extracting an accident.

When none of the three signals is present, the cheapest, most honest, most readable thing to do is what every senior engineer eventually learns to do without flinching:

Write it twice.

Two functions, side by side, each clear about what it does. When they diverge, they diverge cleanly. When they converge for a real reason, you will recognize the third signal, and you will extract from a position of knowledge instead of one of fear.

Chapter IV

Notes & Sources

Where the argument came from, and where it goes next.

This essay is not original. The clearest articulation I know of the “wrong abstraction” idea belongs to Sandi Metz, in a 2016 talk and the blog post that followed. What I have tried to add is a closer accounting of which currencies you pay in, and a small set of decision rules that survive contact with deadlines.

Footnotes

1. The “rule of three” is older than software. The Pragmatic Programmer attributes it to Don Roberts. It applies to refactoring as well as to extraction; both call for waiting until a pattern is unmistakable before responding to it.

2. “Lock-in” here is borrowed from the API-design literature. A function shared by two callers is a one-line API; the engineering discipline you would apply to a public crate’s API surface is the same discipline you should apply to it.
