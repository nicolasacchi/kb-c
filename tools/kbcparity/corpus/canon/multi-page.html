Chapter 01

When to panic

Panics aren’t errors. They’re the rejection of the entire premise that the program could continue. Treat them as such.

The mental model

A panic! is the program saying I am no longer in a state I can reason about. It unwinds the stack, runs destructors, and returns control to whoever invoked the thread — usually with a process abort.

fn divide(a: i64, b: i64) -> i64 {
    if b == 0 {
        panic!("division by zero is not a recoverable condition");
    }
    a / b
}

This is fine in a binary. In a library, it’s a contract violation: callers can’t catch this without spawning a new thread. Library code panics only when an invariant is broken so badly that returning Err would be a lie.

If your library panics on bad input, you’ve made the input the caller’s problem twice.

What to use instead

For anything that can occur in the normal operation of well-behaved code — missing files, parse failures, network blips — return Result. Save panics for “impossible”.

Chapter 02

Result, the workhorse

Ninety percent of error handling is just Result<T, E> and the ? operator. The remaining ten is what this guide is mostly about.

The shape

enum Result<T, E> {
    Ok(T),
    Err(E),
}

That’s the entire abstraction. Every fallible operation in the standard library returns one of these.

The ? operator

fn read_config() -> Result<Config, io::Error> {
    let s = std::fs::read_to_string("config.toml")?;
    let c = parse(&s)?;  // assumes parse returns Result<_, io::Error>
    Ok(c)
}

The ? propagates the error if it’s an Err, unwraps it if it’s an Ok. It also calls .into() on the error type, which is how thiserror’s #[from] derives kick in.

Chapter 03

The Error trait

Error is the trait that lets your error types compose. Implementing it costs almost nothing. Skipping it costs you forever.

The trait

pub trait Error: Debug + Display {
    fn source(&self) -> Option<&(dyn Error + 'static)> { None }
}

Three things matter: Debug (for developer logs), Display (for users), and source (for chaining). Most error libraries write all three for you.

thiserror

#[derive(thiserror::Error, Debug)]
pub enum DbError {
    #[error("connection failed: {0}")]
    Connect(#[source] io::Error),
    #[error("query timed out after {0:?}")]
    Timeout(Duration),
    #[error("constraint violated")]
    Constraint,
}

You get Display from the format string, source from #[source], and From<io::Error> if you swap #[source] for #[from]. That’s the whole library.

Chapter 04

Patterns & anti-patterns

A short, opinionated list. Memorize the first three and you’ll never write a confused error type again.

Do

  • Use thiserror in libraries. Typed errors compose, strings don’t.
  • Use anyhow in binaries. One error type, one box, full backtrace.
  • Add .context() at boundaries. Not at every layer.

Don’t

  • Don’t unwrap() in library code. Even “this can’t happen” should return a typed variant.
  • Don’t mix anyhow and thiserror in the same module. Pick a layer.
  • Don’t make errors carry data callers can’t use. The error is a story for humans; data is for the happy path.

One more thing

If you find yourself reaching for Box<dyn Error>, ask whether you actually want anyhow::Error. The answer is almost always yes.
