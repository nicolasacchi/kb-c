SEV-1 INC-0315 · checkout-api · 2024-03-15 page 1 / 4

Postmortem

Checkout returned 500s for 47 minutes after a routine config push

A single mistyped boolean in our feature-flag service silently disabled connection pooling on the checkout cluster. Latencies climbed for 11 minutes before the SLO burn alert fired; we restored service by reverting the flag.

What happened

At 14:03 UTC, an engineer pushed a config change to the feature-flag service intending to enable a new A/B test. The change accidentally toggled the checkout.pool.enabled flag from true to "true". Our flag library treats string values as truthy on read but as missing on bootstrap, which silently fell back to the default — false.

Checkout pods rolled their connections every 90 seconds. Within ~12 minutes, all instances were holding zero pooled connections. Each request opened a fresh TCP+TLS handshake to Postgres. Throughput collapsed; the cluster started returning 500s as request queues overflowed.

tl;dr A type-coercion quirk in our flag library let a string masquerade as a missing value during bootstrap. The default for the missing case was the unsafe one. Both bugs needed to align — and they did.

Status

Resolved at 14:50 UTC by reverting the flag. Three follow-up action items are P0 and tracked on the next page. The flag library has been patched to treat string “true” / “false” as their boolean counterparts at every read site.
