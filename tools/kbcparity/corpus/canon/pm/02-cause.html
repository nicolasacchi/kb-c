Page 03 — Root Cause

Two bugs, one trigger

Neither bug alone would have caused an outage. They had been coexisting in production for ~14 months. The config push was the first touch that activated both at once.

The bug chain

config push flag library checkout pool ───────────── ──────────── ────────────── "checkout.pool.enabled" ─→ parseValue("true") ─→ pool.enabled = ? value: "true" ⚠ string returns undefined reads undefined │ │ ▼ ▼ fallback to default default is false ⚠ unsafe │ ▼ pool disabled silently

Bug 1 · String values dropped on bootstrap

The flag library has two read paths: get() and bootstrap(). get() coerces strings; bootstrap() validates types strictly and returns undefined on mismatch. Pool config is read once at bootstrap.

// flags-lib/src/bootstrap.ts
function bootstrap<T>(key: string, schema: Schema<T>): T | undefined {
  const raw = store.read(key);
- if (typeof raw !== schema.type) return undefined;
+ const coerced = coerce(raw, schema);
+ if (coerced === undefined) return undefined;
  return coerced;
}

Bug 2 · Unsafe default on missing pool config

The pool initializer treated “config missing” as “user opted out of pooling.” This was a deliberate decision in 2023 — pooling was new, and we wanted opt-in. We forgot to flip the default after pooling became mandatory eight months ago.

// checkout/pool.ts
const cfg = flags.bootstrap("checkout.pool.enabled", boolean);
- this.enabled = cfg ?? false;   // 2023: opt-in
+ this.enabled = cfg ?? true;    // 2024: pooling is mandatory
+ if (cfg === undefined) log.warn("pool.enabled defaulted; investigate");

Why didn’t we catch this earlier?

The integration tests for the flag library use get(), not bootstrap(). The pool integration tests pass an explicit boolean, never relying on the default. Both bugs lived in the seam between two well-tested components.
